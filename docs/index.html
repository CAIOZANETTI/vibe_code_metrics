Guia rápido: usar o vcm num protótipo

Passo a passo para aplicar o método a um projeto de engenharia em Python, do zero ao primeiro cartão de retrospectiva com radar de semáforo. Como funciona por dentro: arquitetura.md. Regras de código: estilo.md.

1. Instalar

O vcm é instalado como ferramenta do uv, direto do GitHub:

uv tool install git+https://github.com/CAIOZANETTI/vibe_code_metrics
vcm --help

Para atualizar: uv tool upgrade vibe-code-metrics.

2. Preparar o protótipo

O uv init cria o pyproject.toml e a pasta src/calculo/:

mkdir meu-prototipo && cd meu-prototipo
git init
uv init --package --name calculo
uv add numpy pandas
uv add --dev pytest
vcm iniciar . --pacote calculo
git add -A && git commit -m "Início do protótipo com vcm"

O vcm iniciar cria, sem sobrescrever o que já existe:

Arquivo Para quê
vcm.yaml onde está o código, os testes e o conjunto de referência
CLAUDE.md suas regras e o ciclo de trabalho, lidos por todo agente
docs/estilo.md Python em português, Python calcula, HTML apresenta, SI
.claude/agents/executor-sonnet.md, executor-haiku.md executores com modelo fixado
src/calculo/referencia.py casos de cálculo usados para medir determinismo, tempo e memória
tests/test_referencia.py o hash de referência é estável
.github/workflows/vcm.yml retrospectiva automática em cada PR

3. O conjunto de referência

Coloque em src/calculo/referencia.py os cálculos que não podem mudar de resultado sem querer, por exemplo a linha piezométrica, o dimensionamento de uma seção ou um volume de corte e aterro. A cada iteração, o vcm:

  • roda o conjunto N vezes e confere se o hash é sempre o mesmo (determinismo);
  • mede o tempo e o pico de memória (eficiência).

A última linha impressa precisa ser um JSON: {"hash": ..., "tempo_ms": ..., "pico_ram_mb": ...}. O modelo gerado já faz isso.

4. O ciclo de cada iteração

flowchart LR
    E["Especificar a tarefa<br/>(você + Opus)"] --> X["Executar<br/>Sonnet ou Haiku"]
    X --> C["Commit"]
    C --> B["vcm balanco BASE HEAD"]
    B --> D{"Decisão"}
    D -->|REVERTER| R["git revert"]
    D -->|MANTER| M["seguir"]
    D -->|DECISAO_HUMANA| H["você decide e registra"]

Depois de cada commit (ou par de commits) de uma tarefa, meça e abra o cartão com radar e semáforo (results/iteracoes/<base>_<alvo>.html):

vcm balanco HEAD~1 HEAD
open results/iteracoes/*.html

No Linux, troque open por xdg-open; no Windows, por start.

O cartão responde, com números:

  • ficou mais eficiente?
  • ficou mais determinístico?
  • ficou mais enxuto?
  • ficou mais robusto?
  • perdeu algo?

O radar compara antes e depois por dimensão (1,0 = igual; maior é melhor). O semáforo mostra o estado atual de cada dimensão:

  • 🟢 dentro do limite;
  • 🟡 atenção;
  • 🔴 fora do limite;
  • ⚪ sem medição.

Os limites padrão podem ser ajustados em vcm.yaml, na chave limites.

5. Usar os agentes

Na sessão do Claude Code, o Opus é o gerente. Peça explicitamente:

"Use o executor-sonnet para implementar X com testes, numa worktree. Depois rode o balanço."

Tarefa Agente
Cálculo novo, módulo com lógica, protótipo de alternativa executor-sonnet
Tabelas de dados, ajustes de lint, testes a partir de exemplos executor-haiku
Decompor, revisar, integrar, decidir trocas sessão principal (Opus)

Cada execução pode ser registrada para comparar custo e qualidade entre modelos:

Registrar uma execução e ver os tokens por tarefa aprovada, por modelo:

uv run python -c "from vcm import agentes; agentes.registrar(modelo='claude-sonnet-5-5', tarefa='...', tokens=..., duracao_s=..., aprovado=True)"
vcm agentes

Gasto dos agentes (automático)

O vcm balanco lê os logs locais do Claude Code (~/.claude/projects) e mostra no cartão quanto os agentes gastaram entre os dois commits, por modelo, em tokens e em custo equivalente de API. Para ver tudo de uma sessão, por agente (tipo, tarefa, modelo, tokens, duração, custo), e o registro próprio do projeto, quando existir:

vcm sessoes --saida results/sessoes
vcm agentes --pdca pdca/agentes.jsonl

Em plano de assinatura o custo é "equivalente de API", não o gasto real.

6. Comparar alternativas (teses)

Quando houver dúvida entre duas formas de fazer, por exemplo NumPy × Polars, não escolha por gosto: implemente as duas atrás da mesma interface, meça e registre. O exemplo completo está na tese T005 deste repositório (theses/T005-perda-de-carga/ e src/vcm/prototipos/perda_de_carga/): dados sintéticos, gabarito independente, runner com repetições e relatório HTML.

7. Calibrar o ruído

Antes de confiar em "ficou mais eficiente", meça quanto as métricas oscilam sem mudança de código:

uv run python -c "from pathlib import Path; from vcm import ruido; ruido.gravar(ruido.estimar(ruido.medir_repetido(Path('.'), repeticoes=3)))"

O balanço passa a usar results/ruido.parquet automaticamente.

8. Problemas comuns

Sintoma Causa provável
"Ficou mais determinístico?" = sem medição referencia.comando ausente no vcm.yaml ou o módulo não imprime o JSON
Determinismo < 1,0 com NumPy Número de threads do BLAS variando; fixe OPENBLAS_NUM_THREADS (ver repertório do NumPy)
Balanço lento A suíte de testes roda dentro da medição; use --sem-testes para uma leitura rápida
"Pico de RAM" sem medição no Windows O conjunto de referência mede memória com psutil; instale com uv add --dev psutil
unrecognized arguments: # ... no Mac O zsh não aceita comentário na mesma linha do comando; rode setopt interactivecomments (ou ponha no ~/.zshrc)
Balanço com --sem-testes e depois sem a opção Desde a versão atual o vcm remede o commit quando faltam os testes; em versões antigas, use --refazer
REVERTER inesperado Veja a linha vermelha do cartão: teste falhando, alerta de segurança ou hash instável

Arquitetura de funcionamento

Vibe Code Metrics é um laboratório de decisões técnicas para desenvolvimento assistido por IA. A IA propõe, o código executa, os testes verificam, as métricas comparam e o humano decide. O próprio repositório é desenvolvido com o seu método (tese T000).

Versão 0.4 · 02/11/2026 · Status: em uso no projetos_em_camadas. Plano de execução: plano.md. Regras de código: estilo.md.

1. Ideia em uma página

O repositório não escolhe ferramentas por gosto. Ele mantém um repertório de alternativas (NumPy, Polars, Parquet, NetworkX, JSON-LD, Haiku, Sonnet, Opus, Fable, Codex, modelos locais…), testa essas alternativas em teses com gabarito próprio e usa as evidências para recomendar o que usar em cada perfil de problema. Cada iteração de código termina com uma retrospectiva medida: ficou mais eficiente, mais determinístico, mais enxuto, mais robusto? Perdeu algo? Vale continuar?

Na prática: o instrumento e o projeto medido

O vcm é um instrumento instalado no computador, como uma trena: não fica dentro do projeto e não precisa do vibe_code_metrics clonado. Ele lê o git local da pasta onde é chamado e grava o resultado nessa mesma pasta.

    T -->|"grava"| R
    C -.->|"orienta o Claude Code"| G
De onde vem O que o vcm tira dali
vcm.yaml do projeto pastas do código, pasta de testes, comando de referência, dependências extras dos testes, limites do semáforo
git local (dois commits) código-fonte medido em cópias temporárias: complexidade, densidade, dependências, segurança, testes, cobertura, reprodutibilidade, tempo e memória
~/.claude/projects (logs do Claude Code) chamadas, tokens e custo equivalente de API por modelo, entre os dois commits, no repositório ou nas worktrees dos agentes
catálogo de preços repertorio/modelos.yaml; noutro projeto, a cópia empacotada no próprio vcm

Consequências:

  • O gasto é por máquina. Os logs ficam no computador onde o Claude Code rodou; trabalho feito noutra máquina ou na nuvem não aparece no cartão.
  • O cache é por pasta. As medições ficam em results/snapshots.parquet de cada cópia do projeto.
  • Nada é enviado. O vcm só lê arquivos locais e grava o cartão; não chama nenhuma API.

3. O ciclo PDCA de uma iteração

Uma iteração é um commit ou um PR. Ela pode ser feita por um humano, por um agente ou por vários agentes coordenados por um gerente.

sequenceDiagram
    actor H as Humano
    participant G as Gerente (Fable/Opus)
    participant W as Executores (Haiku/Sonnet/Opus/Codex)
    participant C as Avaliador + coletores (Python)
    participant R as Histórico (Parquet) + HTML
    H->>G: tese, protocolo e orçamento (Plan)
    G->>W: tarefas pequenas, cada uma com modelo e orçamento
    W->>W: implementa em worktree isolada (Do)
    W->>C: entrega a alteração
    C->>C: confere o hash do avaliador e do gabarito
    C->>C: mede antes × depois (Check)
    C->>R: grava o run e o balanço
    C->>G: veredito por métrica + decisão proposta
    alt eliminatória piorou
        G->>W: reverter
    else melhorou sem perdas
        G->>R: manter (commit)
    else houve troca
        G->>H: decisão humana com a tabela de trocas
    end
    H->>R: aprova o que entra no repertório (Act)

Quem faz o quê

Etapa Responsável Regra que não se negocia
Plan Humano + gerente Protocolo, métricas, tolerâncias e gabarito commitados antes de rodar
Do Executores Cada um trabalha numa worktree isolada, com orçamento de tokens e de tempo
Check Código Python, nunca uma IA Avaliador e gabarito com hash conferido. Alteração detectada invalida o run.
Act Regra automática + humano Reverter e manter podem ser automáticos. Trocas e entradas no repertório exigem aprovação humana.

4. Retrospectiva de iteração

Ao fim de cada iteração, o repositório faz as provocações abaixo. Primeiro responde com números, depois a IA interpreta e, por fim, o humano decide.

Pergunta Métricas (antes × depois) Coleta
Ficou mais eficiente? tempo p50/p95, pico de RAM, custo da iteração pytest-benchmark ou asv, psutil, telemetria
Ficou mais determinístico? fração de execuções idênticas em N repetições, cobertura determinística ponderada runner + numpy
Ficou mais enxuto? SLOC, complexidade média, duplicação, nº de dependências radon, ruff, pyproject.toml
Ficou mais robusto? testes falhando, cobertura, mutation score, alertas de segurança pytest, coverage, mutmut, bandit
Perdeu algo? toda métrica que piorou além do ruído vcm.balanco
Vale continuar nessa linha? tendência das últimas k iterações e ganho ÷ custo histórico em Parquet

    E -->|não| P{"Alguma métrica piorou?"}

Radar de semáforo

O cartão de cada iteração traz duas leituras, ambas calculadas em Python:

  • Radar (relativo): por dimensão, um índice com antes = 1,0, calculado como a média geométrica das razões depois/antes orientadas para que acima de 1,0 seja melhor.
  • Semáforo (absoluto): cada métrica recebe 🟢🟡🔴 por limites (limites_padrao.yaml, que podem ser sobrepostos no vcm.yaml do projeto); a cor da dimensão é a pior entre as suas métricas, e ⚪ indica sem medição.

Exemplos reais: cartão MANTER e cartão REVERTER, gerados no teste ponta a ponta.

O ruído de cada métrica vem de repetições. O tempo de execução oscila alguns por cento, enquanto SLOC não oscila nada. Uma variação dentro do ruído é declarada "igual", nunca "melhorou". O critério de parada funciona como num método iterativo: quando o resíduo para de cair, insistir só gasta tokens.

5. O que é medido passivamente e o que exige protocolo

Passivo (basta instrumentar) Exige protocolo de tese
Tokens e custo equivalente de API por chamada, por agente e por modelo (logs de sessão: implementado; OpenTelemetry adiado) Delimitação da tarefa e critério de "aprovada"
Edições aceitas e rejeitadas, tempo ativo, linhas, commits, PRs Gabarito e tolerâncias por grandeza (cotas: tolerância absoluta)
Trailers Co-Authored-By (o que a IA escreveu) Classificação das intervenções humanas
Testes, cobertura, complexidade e segurança no CI Repetições, variância e intervalos de confiança
Histórico git: churn e retrabalho em 14 dias Linha de base de sistema existente (testes de caracterização)
Pesos de criticidade do índice de determinismo

Cada sessão de agente é marcada com OTEL_RESOURCE_ATTRIBUTES="tese=T000,tarefa=...". É essa marcação que liga a telemetria à tarefa e permite calcular custo por tarefa aprovada. Em planos de assinatura, o custo medido é equivalente de API, não o gasto real. O relatório precisa dizer isso.

6. Multiagente e catálogo de modelos

Configuração atual (decisão do mantenedor): o Opus é o modelo máximo e atua como gerente na sessão principal. Ele delega ao Sonnet e ao Haiku. O Fable não é usado neste momento.

Papel Modelo Faz Não faz
Gerente Opus (sessão principal) Decompõe a fase em tarefas com especificação e teste de aceite; escolhe o executor; integra; roda o balanço; leva trocas ao humano Tarefas mecânicas que um executor faz mais barato
Executor padrão Sonnet Implementação com testes a partir de especificação clara (coletores, protótipos de tese) Decidir arquitetura
Executor mecânico Haiku Entradas de repertório, ajustes de lint, testes a partir de exemplos, resumos Qualquer coisa ambígua
Revisor Opus, ou outro fornecedor na Fase 7 Revisão do que um executor entregou Revisar o próprio código
Avaliador (Check) Python, não é IA vcm balanco, testes, tolerâncias —
Dados confidenciais Modelo local de pesos abertos (Fase 7) Desenho de cliente não sai da máquina —

Cada execução delegada é registrada em results/agentes/execucoes.csv com modelo, tokens, chamadas de ferramenta, duração e se a entrega foi aprovada na integração. Essa é a base de dados da tese T003 (roteamento): a tabela acima é hipótese e passa a ser corrigida pelo custo por tarefa aprovada de cada modelo.

Nenhum nome de modelo fica fixo no código: tudo vem de repertorio/modelos.yaml.

7. Repertório: uma entrada

# repertorio/calculo/numpy.yaml
id: numpy
papel: calculo
quando_considerar: [matriz densa, algebra linear, vetorizacao]
cuidados: [ordem de soma muda com threads do BLAS -> medir determinismo]
evidencias:
  - tese: T005-perda-de-carga
    perfil: {n_trechos: 5000, dtype: float64, operacao: cumsum}
    resultado: venceu
    metricas: {tempo_p50_ms: null, pico_ram_mb: null, deterministico: null}
    run: results/runs/T005/....parquet
status: em_teste   # em_teste | aprovado | rejeitado

Alternativas que não competem entre si não são comparadas. NumPy (cálculo matricial) e Polars (tabelas) costumam cooperar: Polars filtra e junta, .to_numpy() calcula. NetworkX (algoritmos em memória) e JSON-LD (intercâmbio semântico) estão em papéis diferentes.

10. Princípios invioláveis

  1. Cálculo final de engenharia é código determinístico, com teste.
  2. Avaliador e gabarito são trancados: hash conferido a cada run, e os agentes não têm permissão de escrita neles.
  3. Critérios são fixados antes dos resultados, com commit do protocolo antes do run.
  4. Nada vira nota única: as métricas aparecem lado a lado e as eliminatórias vêm primeiro.
  5. Toda variação é comparada com o ruído medido em repetições.
  6. Orçamento por ciclo (tokens, tempo e custo) com critério de parada.
  7. Entrada no repertório exige aprovação humana, registrada em decision.md.
  8. Dados confidenciais só vão para modelos autorizados pela política da tese.

11. O repositório como protótipo dele mesmo (T000)

O desenvolvimento do vcm é a primeira tese. Cada PR deste repositório passa pela retrospectiva (seção 4), e o histórico mostra, ao longo do tempo:

  • quanto custou cada funcionalidade e qual modelo a fez;
  • se o código ficou mais enxuto, robusto e determinístico, ou se degradou;
  • quando uma linha de trabalho convergiu e foi trocada.

Detalhes em theses/T000-autodesenvolvimento.

A geração é determinística: sem data no arquivo, o mesmo Markdown sempre produz os mesmos bytes. Assim o CI consegue detectar HTML desatualizado. A regra está em CLAUDE.md, para que qualquer agente regenere o HTML ao editar a documentação.

DuckDB

Banco SQL analítico embutido no processo, que lê arquivos Parquet e CSV diretamente.

Compete com pandas, polars; coopera com parquet, pandas, polars.

Quando considerar

  • consultas SQL sobre arquivos grandes

  • operação sem servidor

Quando evitar

  • aplicações transacionais de alta frequência de escrita

pandas

Biblioteca de DataFrames para filtrar, juntar e agrupar dados tabulares em Python.

Polars

Biblioteca de DataFrames com motor escrito em Rust, baseada em Apache Arrow e com API de expressões.

  • execução preguiçosa com otimização de consulta

Quando evitar

  • código existente que depende fortemente da API do pandas
  • bibliotecas que aceitam apenas pandas

Cuidados

  • a API difere do pandas, pois não há índice de linha
  • na execução preguiçosa, o resultado só existe após collect()

Lições da Fase 1 (registradas pelo próprio método)

  • O balanço pegou um problema real. O primeiro cartão (18b6b59 → 8fe6d37) propôs REVERTER por um alerta de segurança novo (B314, leitura de XML sem defusedxml). O alerta foi corrigido, não silenciado, e a troca (+1 dependência) aparece no cartão seguinte.
  • "Enxuto" precisa de contexto. Numa iteração que adiciona funcionalidade, SLOC e dependências sobem por definição. Sem normalização, a regra sempre pede decisão humana. Isso virou item do plano.
  • Determinismo depende de threads. Produto matricial e solve do NumPy mudam de hash entre 1 thread e 4 threads, e são estáveis com o número de threads fixo. Isso foi registrado no repertório do NumPy, e a métrica separada virou item do plano.
  • O gerente também erra. Um commit do Opus entrou com teste falhando, porque o código de saída do pytest foi mascarado num pipeline de shell. O balanço seguinte propôs REVERTER e o erro foi corrigido no commit seguinte. Regra: set -o pipefail em todo pipeline de verificação.
  • Agentes em paralelo duplicam utilidades. O executor da T005 não via o vcm.formatacao, criado ao mesmo tempo pelo gerente, e escreveu o seu próprio. O gerente unificou na integração. A especificação deve listar os módulos compartilhados em construção.
  • Interfaces entre executores paralelos divergem em semântica, não em assinatura. O executor da configuração tratou limites como sobreposição; o do semáforo, como lista completa. Com limites: {} o semáforo ficou todo cinza. Os testes de cada um passavam, e só o teste ponta a ponta revelou o problema. Regra: a especificação deve dizer o significado de cada campo compartilhado, e toda integração termina com um teste ponta a ponta.
  • O executor também corrige o gerente. A especificação do radar tinha um erro de sinal no expoente. O executor detectou, explicou e implementou o sinal correto.
  • Eficiência só se compara com o mesmo trabalho. Ao acrescentar um cálculo ao conjunto de referência, o tempo sobe por mais trabalho, não por código pior. Agora o hash da referência identifica o trabalho; se ele muda, tempo e memória viram informativos.
  • Ruído medido neste repositório (3 repetições): tempo de referência ±6% (faixa aceita 12%), pico de memória ±0,1%, tempo da suíte ±1,3%.
  • Tempo curto exige tolerância absoluta. No teste da main recém-publicada, uma iteração que só acrescentou um comentário deu DECISAO_HUMANA: o cálculo de referência de ~10 ms oscilou +23%. Correção com lógica de engenharia: piso absoluto de ruído (5 ms; 2 MB) e ruído automático = 2 × oscilação observada nas repetições do próprio snapshot. A mesma mudança agora dá SEM_GANHO, e a iteração sem semente continua REVERTER.
  • Portabilidade revisada antes da operação. O referencia.py gerado usava o módulo resource, que não existe no Windows, e no macOS a unidade de memória é outra. Agora a medição é portável (vcm.medicao), e a memória fica "sem medição" quando não há como medir, sem quebrar.
  • Projeto real ≠ projeto de exemplo. O primeiro projeto real não tinha pyproject.toml, tinha o pacote na raiz, dependências opcionais usadas pelos testes e um PDCA próprio com outra definição de "determinismo". Nenhum desses casos aparecia nos testes ponta a ponta com projetos criados do zero. Regra: diagnóstico só leitura antes de toda adoção.
  • Executores em paralelo precisam de cópias isoladas também no projeto de destino. Dois executores na mesma pasta do projetos_em_camadas compartilharam o ambiente uv: um rodava uv sync enquanto o outro rodava testes, e apareceram falhas fantasmas. Sozinho, o resultado foi estável. Regra: paralelo só com worktree; na mesma pasta, em sequência.
  • A régua do projeto de destino também pega o gerente. O determinismo.py do projeto em camadas reprovou uma lição registrada pelo Opus com formato errado. Respeitar e rodar as réguas existentes é parte da adoção.
  • Os logs de sessão mentem duas vezes se não forem lidos com cuidado. A mesma resposta aparece em várias linhas (até 7×), e a retomada da sessão noutro diretório copia o histórico para outra pasta de projeto. Somando tudo, o custo saiu US$ 64,55; filtrando por pasta, US$ 29,87; deduplicando globalmente pelo message.id, US$ 43,01, contra US$ 42,39 da plataforma. Regra: conferir toda telemetria contra uma fonte independente antes de confiar nela.
  • O gerente é o maior custo. Na rodada da Fase 2, Opus US$ 5,01 × Sonnet US$ 0,33 × Haiku US$ 0,02. O contexto longo da sessão principal (leitura de cache) domina. Isso é dado para a T003.
  • Worktrees de agentes nasceram da main. (Resolvido: com o trabalho na main, as worktrees já nascem com o projeto.) Os executores precisaram trazer a branch de trabalho. Até a branch ir para a main, a especificação de cada tarefa precisa dizer a base.

Estilo de código do repertório

Regras do mantenedor. Valem para humanos e para todos os agentes. Não são negociáveis: uma alteração que as viola é revertida, mesmo que melhore as métricas.

1. As quatro regras

# Regra Na prática
1 Python em português Nomes de variáveis, funções, classes, módulos, docstrings, comentários e mensagens em português. Palavras-chave da linguagem e APIs de bibliotecas ficam como são.
2 Python calcula Todo cálculo, agregação, estatística, conversão de unidade e decisão acontece em Python. Nenhum cálculo vai para outra linguagem.
3 HTML/JS apresentam HTML, CSS e JavaScript só exibem o que o Python já calculou: tabelas, gráficos, navegação e filtros visuais. JS não soma, não converte, não decide.
4 Sistema métrico (SI) Unidades do Sistema Internacional e as usuais no Brasil (m, mm, m³/s, L/s, kPa, m.c.a., kN, MPa, °C). Nada de pés, polegadas, psi ou galões, nem na entrada nem na saída.

2. Python em português

import numpy as np


def perda_de_carga_hazen_williams(
    vazao_m3s: np.ndarray,
    diametro_m: np.ndarray,
    comprimento_m: np.ndarray,
    coef_c: np.ndarray,
) -> np.ndarray:
    """Perda de carga distribuída por trecho (m), fórmula de Hazen-Williams (SI)."""
    return 10.67 * comprimento_m * vazao_m3s**1.852 / (coef_c**1.852 * diametro_m**4.87)
  • Nomes descritivos e sem abreviação obscura: vazao_m3s, não q; perda_total_m, não hf_t.
  • Acentos ficam fora dos identificadores (vazao, pressao, funcao) e dentro das docstrings e mensagens.
  • Mensagens de erro e de log também em português: raise ValueError("diâmetro deve ser positivo").
  • Termos técnicos sem tradução consagrada podem ficar como estão (hash, commit, parquet, worktree).

3. Unidade no nome

Toda grandeza física leva a unidade como sufixo do nome. Isso evita a classe de erro mais cara da engenharia, que é a de unidade.

Grandeza Sufixo Exemplo
comprimento, cota, diâmetro _m, _mm cota_terreno_m, diametro_mm
área _m2 area_secao_m2
vazão _m3s, _ls vazao_m3s
velocidade _ms velocidade_ms
pressão _kpa, _mca pressao_mca
força, tensão _kn, _mpa carga_kn, tensao_mpa
tempo _s, _ms, _min tempo_execucao_ms
memória _mb pico_ram_mb
adimensional sem sufixo, nome explícito fator_atrito, coef_c

A conversão de unidade é feita uma vez, na entrada, por função explícita (mm_para_m). O núcleo de cálculo trabalha só em SI.

4. Python calcula de forma vetorizada e determinística

  • NumPy primeiro para cálculo numérico: operações vetorizadas e matriciais, sem laço Python sobre elementos.
  • pandas ou Polars para dados tabulares: filtrar, juntar, agrupar. A escolha entre eles é tese, não gosto (ver T005).
  • Parquet para persistir tabelas; YAML para configuração; JSON Lines para logs brutos.
  • dtype explícito (float64 para engenharia) e np.random.default_rng(semente) sempre com semente.
  • Comparações numéricas com tolerância declarada (np.testing.assert_allclose), nunca == em float.
  • Cota, coordenada e nível usam tolerância absoluta (m), não relativa.
  • Funções puras no núcleo de cálculo: mesma entrada, mesma saída; nada de ler relógio, rede ou estado global.

5. HTML e JavaScript só apresentam

Python (numpy/pandas) --calcula--> tabela/figura pronta --serializa--> HTML (+ Plotly JS)
  • O Python gera o HTML, com Jinja2 para o texto e Plotly para gráficos, já com os valores finais.
  • O JavaScript se limita a renderizar gráficos, alternar abas, ordenar e filtrar tabelas. Valores exibidos vêm prontos e formatados.
  • Formatação brasileira na apresentação: vírgula decimal e ponto de milhar (1.234,56), datas dd/mm/aaaa. A formatação também é feita em Python (vcm.formatacao).
