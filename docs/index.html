Arquitetura de funcionamento

Vibe Code Metrics é um laboratório de decisões técnicas para desenvolvimento assistido por IA. A IA propõe, o código executa, os testes verificam, as métricas comparam e o humano decide. O próprio repositório é desenvolvido com o seu método (tese T000).

Versão 0.2 · 31/10/2026 · Status: protótipo em construção. Plano de execução: plano.md.

1. Ideia em uma página

O repositório não escolhe ferramentas por gosto. Ele mantém um repertório de alternativas (NumPy, Polars, Parquet, NetworkX, JSON-LD, Haiku, Sonnet, Opus, Fable, Codex, modelos locais…), testa essas alternativas em teses com gabarito próprio e usa as evidências para recomendar o que usar em cada perfil de problema. Cada iteração de código termina com uma retrospectiva medida: ficou mais eficiente, mais determinístico, mais enxuto, mais robusto? Perdeu algo? Vale continuar?

2. Componentes

Componente O que é Formato Pasta
Repertório Alternativas classificadas por papel (extração, cálculo, armazenamento, intercâmbio, apresentação, orquestração de IA). Só se compara o que cumpre o mesmo papel. YAML repertorio/
Catálogo de modelos Modelos de IA disponíveis, preço, data de verificação e papéis sugeridos. Atualizado quando um fornecedor lança modelo novo, o que dispara regressão. YAML repertorio/modelos.yaml
Tese Hipótese falsificável + protocolo (métricas, tolerâncias, orçamento, repetições) + gabarito congelado + decisão. Markdown + YAML theses/Txxx-*/
Runner Executa alternativas sobre os mesmos casos, com repetições, isolamento em subprocesso, pico de RAM, hash de saída. Python src/vcm/runners/
Coletores Medição passiva: telemetria do agente, git, análise estática, testes. Python → Parquet src/vcm/coletores/
Avaliador Compara a saída com o gabarito por tolerância declarada. É código determinístico e os agentes não podem alterá-lo. Python theses/*/avaliador.py
Balanço Retrospectiva de iteração: antes × depois, veredito por métrica e decisão proposta. Python src/vcm/balanco.py
Recomendador Consulta as evidências por perfil de problema. Python src/vcm/recomendador.py
Relatórios HTML autocontido com Plotly, um por tese, um por iteração e um painel histórico. HTML results/reports/
Documentação Este Markdown é a fonte. vcm docs gera docs/index.html, e o CI garante que o HTML está em dia. MD → HTML docs/

3. O ciclo PDCA de uma iteração

Uma iteração é um commit ou um PR. Ela pode ser feita por um humano, por um agente ou por vários agentes coordenados por um gerente.

sequenceDiagram
    actor H as Humano
    participant G as Gerente (Fable/Opus)
    participant W as Executores (Haiku/Sonnet/Opus/Codex)
    participant C as Avaliador + coletores (Python)
    participant R as Histórico (Parquet) + HTML
    H->>G: tese, protocolo e orçamento (Plan)
    G->>W: tarefas pequenas, cada uma com modelo e orçamento
    W->>W: implementa em worktree isolada (Do)
    W->>C: entrega a alteração
    C->>C: confere o hash do avaliador e do gabarito
    C->>C: mede antes × depois (Check)
    C->>R: grava o run e o balanço
    C->>G: veredito por métrica + decisão proposta
    alt eliminatória piorou
        G->>W: reverter
    else melhorou sem perdas
        G->>R: manter (commit)
    else houve troca
        G->>H: decisão humana com a tabela de trocas
    end
    H->>R: aprova o que entra no repertório (Act)

Quem faz o quê

Etapa Responsável Regra que não se negocia
Plan Humano + gerente Protocolo, métricas, tolerâncias e gabarito commitados antes de rodar
Do Executores Cada um trabalha numa worktree isolada, com orçamento de tokens e de tempo
Check Código Python, nunca uma IA Avaliador e gabarito com hash conferido. Alteração detectada invalida o run.
Act Regra automática + humano Reverter e manter podem ser automáticos. Trocas e entradas no repertório exigem aprovação humana.

4. Retrospectiva de iteração

Ao fim de cada iteração, o repositório faz as provocações abaixo. Primeiro responde com números, depois a IA interpreta e, por fim, o humano decide.

Pergunta Métricas (antes × depois) Coleta
Ficou mais eficiente? tempo p50/p95, pico de RAM, custo da iteração pytest-benchmark ou asv, psutil, telemetria
Ficou mais determinístico? fração de execuções idênticas em N repetições, cobertura determinística ponderada runner + numpy
Ficou mais enxuto? SLOC, complexidade média, duplicação, nº de dependências radon, ruff, pyproject.toml
Ficou mais robusto? testes falhando, cobertura, mutation score, alertas de segurança pytest, coverage, mutmut, bandit
Perdeu algo? toda métrica que piorou além do ruído vcm.balanco
Vale continuar nessa linha? tendência das últimas k iterações e ganho ÷ custo histórico em Parquet 
flowchart TD
    M["Medir antes × depois<br/>(variação além do ruído)"] --> E{"Alguma eliminatória piorou?<br/>testes · determinismo · segurança"}
    E -->|sim| REV["REVERTER"]
    E -->|não| P{"Alguma métrica piorou?"}
    P -->|sim| HUM["DECISÃO HUMANA<br/>troca registrada com justificativa"]
    P -->|não| G{"Alguma melhorou?"}
    G -->|sim| MAN["MANTER"]
    G -->|não| SG["SEM GANHO"]
    SG --> CV{"3 iterações seguidas sem ganho?"}
    CV -->|sim| PARE["PARAR esta linha<br/>consultar o repertório por alternativa"]
    CV -->|não| MAN2["seguir iterando"]

O ruído de cada métrica vem de repetições. O tempo de execução oscila alguns por cento, enquanto SLOC não oscila nada. Uma variação dentro do ruído é declarada "igual", nunca "melhorou". O critério de parada funciona como num método iterativo: quando o resíduo para de cair, insistir só gasta tokens.

5. O que é medido passivamente e o que exige protocolo

Passivo (basta instrumentar) Exige protocolo de tese
Tokens, custo equivalente de API, latência por chamada (OpenTelemetry do Claude Code, logs de sessão) Delimitação da tarefa e critério de "aprovada"
Edições aceitas e rejeitadas, tempo ativo, linhas, commits, PRs Gabarito e tolerâncias por grandeza (cotas: tolerância absoluta)
Trailers Co-Authored-By (o que a IA escreveu) Classificação das intervenções humanas
Testes, cobertura, complexidade e segurança no CI Repetições, variância e intervalos de confiança
Histórico git: churn e retrabalho em 14 dias Linha de base de sistema existente (testes de caracterização)
Pesos de criticidade do índice de determinismo

Cada sessão de agente é marcada com OTEL_RESOURCE_ATTRIBUTES="tese=T000,tarefa=...". É essa marcação que liga a telemetria à tarefa e permite calcular custo por tarefa aprovada. Em planos de assinatura, o custo medido é equivalente de API, não o gasto real. O relatório precisa dizer isso.

6. Multiagente e catálogo de modelos

Papel Perfil de modelo (a validar na tese T003) Por quê
Gerente / planejador Mais capaz (Fable, Opus) Decompor, priorizar, julgar trocas
Executor de tarefa bem especificada Rápido e barato (Haiku) Especificação clara e teste objetivo
Executor de tarefa com julgamento Intermediário (Sonnet) Bom equilíbrio entre custo e qualidade
Revisor Outro modelo ou outro fornecedor (Codex) Reduz erros correlacionados. Mesmo modelo não é revisão independente.
Dados confidenciais Modelo local de pesos abertos Desenho de cliente não sai da máquina

Esta tabela é hipótese, não regra. A tese T003 mede custo por tarefa aprovada por papel e modelo, e a tabela passa a ser derivada das evidências. Nenhum nome de modelo fica fixo no código: tudo vem de repertorio/modelos.yaml.

7. Repertório: uma entrada

# repertorio/calculo/numpy.yaml
id: numpy
papel: calculo
quando_considerar: [matriz densa, algebra linear, vetorizacao]
cuidados: [ordem de soma muda com threads do BLAS -> medir determinismo]
evidencias:
  - tese: T005-perda-de-carga
    perfil: {n_trechos: 5000, dtype: float64, operacao: cumsum}
    resultado: venceu
    metricas: {tempo_p50_ms: null, pico_ram_mb: null, deterministico: null}
    run: results/runs/T005/....parquet
status: em_teste   # em_teste | aprovado | rejeitado

Alternativas que não competem entre si não são comparadas. NumPy (cálculo matricial) e Polars (tabelas) costumam cooperar: Polars filtra e junta, .to_numpy() calcula. NetworkX (algoritmos em memória) e JSON-LD (intercâmbio semântico) estão em papéis diferentes.

8. Dados e formatos

Dado Formato Por quê
Protocolos, repertório, catálogo de modelos YAML Legível, versionado em git, validado com schema
Runs, telemetria normalizada, histórico de iterações Parquet Colunar, tipado, lido direto por pandas e Polars
Telemetria bruta JSON Lines Como sai dos coletores, sem perda
Hash de entradas e saídas SHA-256 sobre os dados (não sobre os bytes do arquivo) Metadados do Parquet mudam sem os dados mudarem
Documentação e relatórios Markdown → HTML Markdown para editar e versionar, HTML para ler

10. Princípios invioláveis

  1. Cálculo final de engenharia é código determinístico, com teste.
  2. Avaliador e gabarito são trancados: hash conferido a cada run, e os agentes não têm permissão de escrita neles.
  3. Critérios são fixados antes dos resultados, com commit do protocolo antes do run.
  4. Nada vira nota única: as métricas aparecem lado a lado e as eliminatórias vêm primeiro.
  5. Toda variação é comparada com o ruído medido em repetições.
  6. Orçamento por ciclo (tokens, tempo e custo) com critério de parada.
  7. Entrada no repertório exige aprovação humana, registrada em decision.md.
  8. Dados confidenciais só vão para modelos autorizados pela política da tese.

11. O repositório como protótipo dele mesmo (T000)

O desenvolvimento do vcm é a primeira tese. Cada PR deste repositório passa pela retrospectiva (seção 4), e o histórico mostra, ao longo do tempo:

  • quanto custou cada funcionalidade e qual modelo a fez;
  • se o código ficou mais enxuto, robusto e determinístico, ou se degradou;
  • quando uma linha de trabalho convergiu e foi trocada.

Detalhes em theses/T000-autodesenvolvimento.

Fase 0 — Fundação

  • pyproject.toml com uv, pacote vcm em src/, CLI vcm
  • vcm.balanco: tabela antes × depois, veredito com ruído, regra de decisão, convergência, com testes
  • vcm docs: Markdown → HTML único e determinístico, com diagramas Mermaid e --check
  • docs/arquitetura.md e docs/plano.md (este arquivo)
  • CI no GitHub Actions: ruff, pytest e vcm docs --check
  • CLAUDE.md com as regras para agentes
  • Esqueleto da tese T000 (hypothesis.md, protocol.yaml)

Aceite: uv run pytest verde; uv run vcm docs --check verde; HTML abre com navegação e diagramas.

Fase 1 — Retrospectiva automática

Objetivo: toda iteração (commit ou PR) gera o balanço antes × depois sem trabalho manual.

  • vcm snapshot [--ref REF] mede o código em um ref (via git worktree) e grava uma linha em Parquet:
    • enxuto: SLOC e complexidade média (radon), nº de dependências (pyproject.toml)
    • robusto: testes passando e falhando, cobertura (coverage.py), alertas (bandit)
    • eficiente: tempo dos benchmarks marcados (pytest-benchmark) e pico de RAM (psutil)
    • determinístico: N execuções do conjunto de referência, com fração de saídas idênticas
  • Estimar o ruído de cada métrica com repetições e gravar em results/ruido.parquet
  • vcm balanco BASE HEAD: compara dois snapshots, grava results/iteracoes/<id>.parquet e imprime o cartão
  • Cartão da iteração em Markdown e HTML: tabela, respostas às perguntas, decisão proposta, campo de justificativa
  • GitHub Action em PR: roda o balanço contra a base e anexa o cartão HTML como artefato
  • Registrar retroativamente as iterações da Fase 0 como linha de base da T000

Aceite: um PR de teste mostra o cartão com as 6 perguntas respondidas por números; uma regressão proposital em teste resulta em REVERTER.

Fase 2 — Telemetria de agentes

Objetivo: custo, tokens e tempo de cada iteração, ligados à tese e à tarefa.

  • Documentar a ativação: CLAUDE_CODE_ENABLE_TELEMETRY=1, exportador OTLP e OTEL_RESOURCE_ATTRIBUTES=tese=...,tarefa=...
  • Receptor local mínimo (coletor OpenTelemetry com exportador de arquivo, ou receptor OTLP em Python) → JSONL → Parquet
  • Alternativa sem coletor: parser dos logs de sessão locais do Claude Code → Parquet (validar o caminho e o formato atuais antes)
  • repertorio/modelos.yaml: modelo, fornecedor, preço por milhão de tokens (entrada, saída, cache), data e fonte da verificação
  • Custo da iteração no balanço: tokens, custo equivalente de API, nº de chamadas, edições rejeitadas
  • Indicadores: tokens_por_aprovacao, custo_por_aprovacao (incluindo tempo humano), taxa_de_retrabalho

Aceite: uma sessão real de Claude Code numa tarefa da T000 aparece no balanço com custo e tokens; a soma confere com o painel do fornecedor dentro de 5%.

Fase 3 — Repertório, tese e runner

  • Schemas pydantic: entrada de repertório, protocol.yaml, registro de run (campos da seção 10 do README, mais git commit, lockfile, seed, versões do gabarito e do protocolo)
  • vcm tese nova Txxx cria a estrutura da tese a partir de um modelo
  • Runner: mesma entrada para cada alternativa, N repetições, subprocesso isolado, pico de RSS, hash dos dados de saída, tempo p50/p95
  • Avaliador trancado: hash do avaliador e do gabarito gravado no protocolo e conferido no run
  • Separação desenvolvimento/teste no gabarito (holdout congelado)
  • T005 — Perda de carga na adutora: NumPy × Polars × Polars + NumPy
    • caso: perfil de 5 km com N trechos; Hazen-Williams e Darcy-Weisbach
    • gabarito: solução analítica ou de referência com tolerância absoluta (m.c.a.)
    • métricas: tempo, RAM, determinismo (threads 1 × N), SLOC, legibilidade (revisão)

Aceite: vcm tese rodar T005 produz runs em Parquet e um decision.md preenchido com as evidências.

Fase 4 — Relatórios HTML

  • Template base compartilhado com vcm docs (mesma identidade visual)
  • Relatório de tese: protocolo, tabela por alternativa, gráficos Plotly (distribuição de tempo, Pareto custo × qualidade), decisão
  • Relatório de iteração: o cartão da Fase 1, com links
  • Painel histórico: trajetória de cada métrica por iteração, marcando convergência e degradação
  • Índice results/reports/index.html ligando tudo

Aceite: os três relatórios abrem offline (Plotly embutido ou em CDN com fallback) e são gerados de forma determinística.

Fase 5 — Orquestração multiagente

  • Definição de agentes por papel (gerente, executor, revisor) com modelo vindo de modelos.yaml
  • Loop PDCA: o gerente decompõe; o executor trabalha numa worktree; o avaliador confere; o balanço decide
  • Orçamento por ciclo (tokens, tempo, custo) e critério de parada (convergência ou orçamento)
  • Bloqueio de escrita em avaliador e gabarito (permissões do agente + hash conferido)
  • Portão humano para trocas e para entradas no repertório
  • T003 — Roteamento: mesmo conjunto de tarefas com Haiku, Sonnet e Opus como executores; custo por tarefa aprovada

Aceite: um ciclo autônomo de pelo menos 3 iterações numa tarefa da T000, com balanço registrado e pelo menos uma decisão humana pedida e registrada.

Fase 6 — Recomendador

  • Índice de evidências por papel e perfil de problema
  • vcm sugerir --papel calculo --perfil n=5000,dtype=float64 lista as alternativas com evidência, as lacunas e a sugestão de nova tese
  • Integração com o balanço: quando convergir, sugerir alternativa do repertório

Aceite: a consulta para o perfil da T005 retorna a alternativa vencedora com link para o run.

Fase 7 — Multi-fornecedor e política de dados

  • Camada de acesso a modelos (LiteLLM ou adaptadores próprios em adapters/llm/)
  • Codex e pelo menos um modelo local de pesos abertos como alternativas no repertório
  • Política de dados por classe (público, interno, confidencial do cliente) aplicada pelo runner
  • Regressão automática ao incluir um modelo novo no catálogo

Aceite: a mesma tarefa roda em três fornecedores, com custo e qualidade comparáveis no mesmo relatório.

Fase 8 — Primeiro programa experimental

Teses T001 (extração de pranchas), T002 (armazenamento espacial), T003 (roteamento) e T004 (determinismo) aplicadas ao projeto-em-camadas, que é consumido como repositório externo com adaptadores próprios.

Regras de execução deste plano

  1. Um PR por item, ou por grupo pequeno de itens; nada de PR monolítico.
  2. Todo PR atualiza os checkboxes deste arquivo e roda uv run vcm docs.
  3. A partir da Fase 1, todo PR anexa o cartão de retrospectiva. REVERTER bloqueia o merge.
  4. Decisões de arquitetura relevantes viram um registro curto em docs/decisoes/ (formato ADR).
  5. Itens que dependem de informação externa (preços, formatos de log, APIs) são verificados na documentação oficial na hora de implementar, com data e fonte.

Decisões em aberto (para o humano)

  • Qual projeto a referência "Document Parser Benchmark" do README queria citar? (Candidatos: OmniDocBench, olmOCR-Bench, docling-eval.)
  • O uso será por assinatura ou por API? Isso define se o custo reportado é real ou equivalente.
  • Quais classes de dados do projeto-em-camadas podem sair da máquina?
  • Pesos de criticidade iniciais para o índice de determinismo.
