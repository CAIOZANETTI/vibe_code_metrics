Guia rápido: usar o vcm num protótipo

Passo a passo para aplicar o método a um projeto de engenharia em Python, do zero ao primeiro cartão de retrospectiva com radar de semáforo. Como funciona por dentro: arquitetura.md. Regras de código: estilo.md.

Como usar este repositório

O vibe_code_metrics tem dois usos. Escolha o seu:

Você quer… Onde trabalha O que faz
Medir um projeto seu (ex.: projetos_em_camadas) na pasta do projeto instala o vcm, roda vcm iniciar uma vez e vcm balanco a cada iteração
Escolher ferramenta ou skill para uma tarefa nesta documentação consulta o repertório e as skills
Saber se o método está ajudando na pasta do projeto vcm historico e vcm efeito (antes × depois da adoção)
Evoluir o próprio método neste repositório segue o plano; cada mudança passa pelo mesmo balanço (tese T000)

O dia a dia num projeto, com o Claude Code aberto na pasta dele:

  1. Você pede uma tarefa em linguagem natural.
  2. O Claude (gerente) consulta o CLAUDE.md do projeto, o repertório e as skills, divide a tarefa e chama os executores (Sonnet, Haiku).
  3. Depois do commit, vcm balanco HEAD~1 HEAD gera o cartão: radar, semáforo e gasto dos agentes.
  4. REVERTER desfaz; MANTER segue; troca de métricas, você decide e registra.
  5. De tempos em tempos, vcm efeito mostra se o projeto está melhor do que antes da adoção.

Para atualizar o instrumento: uv tool install --force git+https://github.com/CAIOZANETTI/vibe_code_metrics.

1. Instalar

O vcm é instalado como ferramenta do uv, direto do GitHub:

uv tool install git+https://github.com/CAIOZANETTI/vibe_code_metrics
vcm --help

Para atualizar: uv tool upgrade vibe-code-metrics.

2. Preparar o protótipo

O uv init cria o pyproject.toml e a pasta src/calculo/:

mkdir meu-prototipo && cd meu-prototipo
git init
uv init --package --name calculo
uv add numpy pandas
uv add --dev pytest
vcm iniciar . --pacote calculo
git add -A && git commit -m "Início do protótipo com vcm"

O vcm iniciar cria, sem sobrescrever o que já existe:

Arquivo Para quê
vcm.yaml onde está o código, os testes e o conjunto de referência
CLAUDE.md suas regras e o ciclo de trabalho, lidos por todo agente
docs/estilo.md Python em português, Python calcula, HTML apresenta, SI
.claude/agents/executor-sonnet.md, executor-haiku.md executores com modelo fixado
src/calculo/referencia.py casos de cálculo usados para medir determinismo, tempo e memória
tests/test_referencia.py o hash de referência é estável
.github/workflows/vcm.yml retrospectiva automática em cada PR

3. O conjunto de referência

Coloque em src/calculo/referencia.py os cálculos que não podem mudar de resultado sem querer, por exemplo a linha piezométrica, o dimensionamento de uma seção ou um volume de corte e aterro. A cada iteração, o vcm:

  • roda o conjunto N vezes e confere se o hash é sempre o mesmo (determinismo);
  • mede o tempo e o pico de memória (eficiência).

A última linha impressa precisa ser um JSON: {"hash": ..., "tempo_ms": ..., "pico_ram_mb": ...}. O modelo gerado já faz isso.

4. O ciclo de cada iteração

flowchart LR
    E["Especificar a tarefa<br/>(você + Opus)"] --> X["Executar<br/>Sonnet ou Haiku"]
    X --> C["Commit"]
    C --> B["vcm balanco BASE HEAD"]
    B --> D{"Decisão"}
    D -->|REVERTER| R["git revert"]
    D -->|MANTER| M["seguir"]
    D -->|DECISAO_HUMANA| H["você decide e registra"]

Depois de cada commit (ou par de commits) de uma tarefa, meça e abra o cartão com radar e semáforo (results/iteracoes/<base>_<alvo>.html):

vcm balanco HEAD~1 HEAD
open results/iteracoes/*.html

No Linux, troque open por xdg-open; no Windows, por start.

O cartão responde, com números:

  • ficou mais eficiente?
  • ficou mais determinístico?
  • ficou mais enxuto?
  • ficou mais robusto?
  • perdeu algo?

O radar compara antes e depois por dimensão (1,0 = igual; maior é melhor). O semáforo mostra o estado atual de cada dimensão:

  • 🟢 dentro do limite;
  • 🟡 atenção;
  • 🔴 fora do limite;
  • ⚪ sem medição.

Os limites padrão podem ser ajustados em vcm.yaml, na chave limites.

5. Usar os agentes

Na sessão do Claude Code, o Opus é o gerente. Peça explicitamente:

"Use o executor-sonnet para implementar X com testes, numa worktree. Depois rode o balanço."

Tarefa Agente
Cálculo novo, módulo com lógica, protótipo de alternativa executor-sonnet
Tabelas de dados, ajustes de lint, testes a partir de exemplos executor-haiku
Decompor, revisar, integrar, decidir trocas sessão principal (Opus)

Cada execução pode ser registrada para comparar custo e qualidade entre modelos:

Registrar uma execução e ver os tokens por tarefa aprovada, por modelo:

uv run python -c "from vcm import agentes; agentes.registrar(modelo='claude-sonnet-5-5', tarefa='...', tokens=..., duracao_s=..., aprovado=True)"
vcm agentes

Gasto dos agentes (automático)

O vcm balanco lê os logs locais do Claude Code (~/.claude/projects) e mostra no cartão quanto os agentes gastaram entre os dois commits, por modelo, em tokens e em custo equivalente de API. Para ver tudo de uma sessão, por agente (tipo, tarefa, modelo, tokens, duração, custo), e o registro próprio do projeto, quando existir:

vcm sessoes --saida results/sessoes
vcm agentes --pdca pdca/agentes.jsonl

Em plano de assinatura o custo é "equivalente de API", não o gasto real.

6. Comparar alternativas (teses)

Quando houver dúvida entre duas formas de fazer, por exemplo NumPy × Polars, não escolha por gosto: implemente as duas atrás da mesma interface, meça e registre. O exemplo completo está na tese T005 deste repositório (theses/T005-perda-de-carga/ e src/vcm/prototipos/perda_de_carga/): dados sintéticos, gabarito independente, runner com repetições e relatório HTML.

7. Calibrar o ruído

Antes de confiar em "ficou mais eficiente", meça quanto as métricas oscilam sem mudança de código:

uv run python -c "from pathlib import Path; from vcm import ruido; ruido.gravar(ruido.estimar(ruido.medir_repetido(Path('.'), repeticoes=3)))"

O balanço passa a usar results/ruido.parquet automaticamente.

Sintoma Causa provável
"Ficou mais determinístico?" = sem medição referencia.comando ausente no vcm.yaml ou o módulo não imprime o JSON

Arquitetura de funcionamento

Vibe Code Metrics é um laboratório de decisões técnicas para desenvolvimento assistido por IA. A IA propõe, o código executa, os testes verificam, as métricas comparam e o humano decide. O próprio repositório é desenvolvido com o seu método (tese T000).

De onde vem O que o vcm tira dali
vcm.yaml do projeto pastas do código, pasta de testes, comando de referência, dependências extras dos testes, limites do semáforo
git local (dois commits) código-fonte medido em cópias temporárias: complexidade, densidade, dependências, segurança, testes, cobertura, reprodutibilidade, tempo e memória
~/.claude/projects (logs do Claude Code) chamadas, tokens e custo equivalente de API por modelo, entre os dois commits, no repositório ou nas worktrees dos agentes
catálogo de preços repertorio/modelos.yaml; noutro projeto, a cópia empacotada no próprio vcm

Consequências:

  • O gasto é por máquina. Os logs ficam no computador onde o Claude Code rodou; trabalho feito noutra máquina ou na nuvem não aparece no cartão.
  • O cache é por pasta. As medições ficam em results/snapshots.parquet de cada cópia do projeto.
  • Nada é enviado. O vcm só lê arquivos locais e grava o cartão; não chama nenhuma API.

3. O ciclo PDCA de uma iteração

Uma iteração é um commit ou um PR. Ela pode ser feita por um humano, por um agente ou por vários agentes coordenados por um gerente.

    participant W as Executores (Haiku/Sonnet/Opus/Codex)
    participant C as Avaliador + coletores (Python)
    participant R as Histórico (Parquet) + HTML
    H->>G: tese, protocolo e orçamento (Plan)
    G->>W: tarefas pequenas, cada uma com modelo e orçamento
    W->>W: implementa em worktree isolada (Do)
    W->>C: entrega a alteração
    C->>C: confere o hash do avaliador e do gabarito

    C->>G: veredito por métrica + decisão proposta

Quem faz o quê

Etapa Responsável Regra que não se negocia

4. Retrospectiva de iteração

Ao fim de cada iteração, o repositório faz as provocações abaixo. Primeiro responde com números, depois a IA interpreta e, por fim, o humano decide.

Pergunta Métricas (antes × depois) Coleta
Ficou mais eficiente? tempo p50/p95, pico de RAM, custo da iteração pytest-benchmark ou asv, psutil, telemetria
Ficou mais determinístico? fração de execuções idênticas em N repetições, cobertura determinística ponderada runner + numpy
Ficou mais enxuto? SLOC, complexidade média, duplicação, nº de dependências radon, ruff, pyproject.toml
Ficou mais robusto? testes falhando, cobertura, mutation score, alertas de segurança pytest, coverage, mutmut, bandit
Perdeu algo? toda métrica que piorou além do ruído vcm.balanco
Vale continuar nessa linha? tendência das últimas k iterações e ganho ÷ custo histórico em Parquet

Radar de semáforo

O cartão de cada iteração traz duas leituras, ambas calculadas em Python:

  • Radar (relativo): por dimensão, um índice com antes = 1,0, calculado como a média geométrica das razões depois/antes orientadas para que acima de 1,0 seja melhor.
  • Semáforo (absoluto): cada métrica recebe 🟢🟡🔴 por limites (limites_padrao.yaml, que podem ser sobrepostos no vcm.yaml do projeto); a cor da dimensão é a pior entre as suas métricas, e ⚪ indica sem medição.

Exemplos reais: cartão MANTER e cartão REVERTER, gerados no teste ponta a ponta.

O ruído de cada métrica vem de repetições. O tempo de execução oscila alguns por cento, enquanto SLOC não oscila nada. Uma variação dentro do ruído é declarada "igual", nunca "melhorou". O critério de parada funciona como num método iterativo: quando o resíduo para de cair, insistir só gasta tokens.

Pesos de criticidade do índice de determinismo

Cada sessão de agente é marcada com OTEL_RESOURCE_ATTRIBUTES="tese=T000,tarefa=...". É essa marcação que liga a telemetria à tarefa e permite calcular custo por tarefa aprovada. Em planos de assinatura, o custo medido é equivalente de API, não o gasto real. O relatório precisa dizer isso.

6. Multiagente e catálogo de modelos

Configuração atual (decisão do mantenedor): o Opus é o modelo máximo e atua como gerente na sessão principal. Ele delega ao Sonnet e ao Haiku. O Fable não é usado neste momento.

Papel Modelo Faz Não faz

Cada execução delegada é registrada em results/agentes/execucoes.csv com modelo, tokens, chamadas de ferramenta, duração e se a entrega foi aprovada na integração. Essa é a base de dados da tese T003 (roteamento): a tabela acima é hipótese e passa a ser corrigida pelo custo por tarefa aprovada de cada modelo.

Nenhum nome de modelo fica fixo no código: tudo vem de repertorio/modelos.yaml.

Modelo × skill × ferramenta

Três escolhas independentes compõem cada tarefa:

Escolha Pergunta Onde está
Modelo quem executa (custo × capacidade) repertorio/modelos.yaml, tabela acima
Skill como conduzir (passo a passo, cuidados, quando parar) skills.md
Ferramenta com o que calcular (biblioteca Python) repertorio.md

Uma tarefa repetível de domínio (ler uma prancha, quantificar uma vala) vira skill do projeto, com o cálculo em código determinístico; a skill orienta o agente e aponta o código. Skills externas entram como candidatas: lidas antes de instalar, porque podem trazer scripts que rodam na máquina.

10. Princípios invioláveis

  1. Cálculo final de engenharia é código determinístico, com teste.
  2. Avaliador e gabarito são trancados: hash conferido a cada run, e os agentes não têm permissão de escrita neles.
  3. Critérios são fixados antes dos resultados, com commit do protocolo antes do run.
  4. Nada vira nota única: as métricas aparecem lado a lado e as eliminatórias vêm primeiro.
  5. Toda variação é comparada com o ruído medido em repetições.
  6. Orçamento por ciclo (tokens, tempo e custo) com critério de parada.
  7. Entrada no repertório exige aprovação humana, registrada em decision.md.
  8. Dados confidenciais só vão para modelos autorizados pela política da tese.

Numba

Compilador JIT que traduz funções Python e NumPy em código de máquina via LLVM.

Coopera com numpy, scipy, sympy.

Quando considerar

  • laços numéricos escalares que não vetorizam bem em NumPy (marcha de cálculo trecho a trecho, iterações com dependência entre passos)
  • funções chamadas muitas vezes sobre arrays grandes, em que o custo de compilação se paga
  • paralelismo simples em laços independentes com prange
  • manter o código Python legível em vez de reescrevê-lo em C ou Rust

Quando evitar

  • funções curtas ou chamadas poucas vezes, em que a compilação custa mais que o ganho
  • código que usa DataFrames, strings, objetos Python ou bibliotecas fora do subconjunto suportado
  • cálculo que já se expressa em operações vetorizadas de NumPy

Cuidados

  • a primeira chamada compila e é lenta; cache=True guarda a compilação em disco
  • fastmath=True permite reordenar operações de ponto flutuante e pode mudar o resultado; evitar quando o resultado precisar ser reprodutível
  • com parallel=True a ordem das reduções pode variar entre execuções; medir determinismo antes de adotar
  • o Numba aceita só algumas versões do NumPy e do Python; conferir a compatibilidade antes de atualizar o NumPy
  • variáveis globais são tratadas como constantes no momento da compilação
  • erros de tipagem são difíceis de ler; testar a função também com NUMBA_DISABLE_JIT para depurar

Repositório: https://github.com/numba/numba

NumPy

Arrays N-dimensionais e álgebra linear vetorizada em Python.

Coopera com pandas, polars, plotly, scipy, numba, xarray, pint.

Quando considerar

  • cálculo matricial e vetorizado
  • álgebra linear
  • base comum do ecossistema numérico (pandas, SciPy e Plotly trocam dados com arrays NumPy)
  • cálculo elemento a elemento sobre milhares de seções, trechos ou nós sem laços em Python
  • dtype explícito (float64, int32) torna o comportamento numérico previsível e documentável

Quando evitar

  • dados tabulares heterogêneos com junções e agrupamentos
  • dados com dimensões nomeadas e coordenadas (tempo, cota, estação), em que o rótulo evita erro de eixo (considerar xarray)
  • laços escalares que não vetorizam, em que um compilador JIT pode ser mais adequado (considerar numba)

Cuidados

  • a ordem das somas pode variar com o número de threads do BLAS; medir determinismo
  • {'medido em 31/10/2026 (vcm.coletores.determinismo, 4 núcleos)': 'produto matricial 500×500 e solve 200×200 mudam de hash entre 1 thread e o padrão; com threads fixas, 100% estável; cumsum não muda. Fixar OPENBLAS_NUM_THREADS quando o resultado precisar ser reprodutível bit a bit'}
  • float32 acumula erro diferente de float64; declarar o dtype e a tolerância absoluta ou relativa nos testes (np.testing.assert_allclose com atol e rtol explícitos)
  • o NumPy 2 mudou as regras de promoção de tipos (NEP 50) e removeu aliases antigos; código escrito para 1.x pode mudar de dtype
  • fatias são vistas, não cópias; alterar uma fatia altera o array original

Repositório: https://github.com/numpy/numpy

SciPy

Algoritmos científicos sobre NumPy, como otimização, interpolação, estatística e álgebra linear esparsa.

Coopera com numpy, pandas, sympy, numba, xarray.

Quando considerar

  • otimização numérica
  • interpolação
  • estatística
  • álgebra linear esparsa
  • sistemas grandes e esparsos (redes de tubulação, malhas, matrizes de rigidez) com scipy.sparse
  • integração numérica e equações diferenciais ordinárias (scipy.integrate) com tolerâncias declaradas
  • raízes e ajuste de curvas (scipy.optimize) para equações implícitas, como Colebrook-White

Quando evitar

  • manipulação de tabelas com junções e agrupamentos
  • álgebra simbólica ou derivação exata (considerar sympy)
  • quando uma operação simples de NumPy já resolve

Cuidados

  • solvers iterativos dependem de tolerância e critério de parada; declarar ambos
  • rotinas de otimização podem convergir para mínimo local ou falhar sem lançar erro; verificar o campo success do resultado e registrar o ponto inicial
  • interpoladores tratam de formas diferentes o que está fora do intervalo dos dados (erro, constante, extrapolação); declarar o comportamento escolhido
  • herda do NumPy a variação de somas com threads do BLAS; fixar threads quando o resultado precisar ser reprodutível bit a bit
  • a versão 1.18 exige Python 3.12 ou mais recente; conferir a versão do Python do projeto
  • algoritmos estocásticos (por exemplo, evolução diferencial) exigem semente fixa para serem determinísticos

Repositório: https://github.com/scipy/scipy

SymPy

Álgebra simbólica em Python puro, com derivação, integração, resolução de equações e geração de código.

Coopera com numpy, scipy, numba, pint.

Quando considerar

  • deduzir e conferir uma fórmula de engenharia (derivadas, integrais, simplificação) antes de implementá-la
  • gerar a função numérica a partir da expressão simbólica com lambdify, mantendo a fórmula documentada e testável
  • obter por solução exata um caso de teste que o código numérico deve reproduzir
  • resolver sistemas pequenos de equações com solução em forma fechada

Quando evitar

  • cálculo numérico pesado sobre arrays grandes, em que o simbólico é lento (usar numpy ou scipy)
  • caminho de produção sensível a tempo, se a expressão simbólica for montada a cada chamada
  • equações sem solução fechada, melhor resolvidas por métodos numéricos (scipy)

Cuidados

  • simplify e solve podem demorar muito ou devolver formas diferentes entre versões; fixar a versão e não depender da forma textual do resultado
  • lambdify gera função NumPy; conferir o módulo de destino e o dtype
  • usar Rational ou inteiros em vez de float dentro da expressão evita erro de arredondamento antes da hora
  • a última versão publicada (1.14.0) é de 2025-04; verificar se há versão mais nova antes de adotar

Repositório: https://github.com/sympy/sympy

xarray

Arrays N-dimensionais com dimensões nomeadas, coordenadas e atributos, sobre NumPy e pandas.

Coopera com numpy, pandas, pint.

Quando considerar

  • dados em grade ou multidimensionais (tempo × estação, tempo × cota × posição, séries de chuva, campos de modelo)
  • operar por nome de dimensão, sem depender da ordem dos eixos, o que reduz erros de eixo
  • ler e gravar NetCDF e Zarr, formatos comuns de dados hidrológicos e climáticos
  • manter metadados e unidades declaradas junto dos valores (atributos)

Quando evitar

  • dados tabulares simples, melhor atendidos por pandas ou Polars
  • cálculo sobre um array sem coordenadas, em que NumPy basta

Cuidados

  • o alinhamento automático por coordenadas faz junção implícita; coordenadas float diferentes por arredondamento geram eixo vazio ou NaN sem aviso
  • depende de NumPy e pandas; o cálculo de fundo é do NumPy e herda sua variação de threads
  • arrays com Dask são preguiçosos e o resultado só existe após compute()
  • as unidades ficam em atributos de texto e não são verificadas; para checagem, combinar com pint
  • a versão segue o calendário (2026.9.0) e a API muda entre versões; fixar a versão

Repositório: https://github.com/pydata/xarray

DuckDB

Banco SQL analítico embutido no processo, que lê arquivos Parquet e CSV diretamente.

Compete com pandas, polars; coopera com parquet, pandas, polars, sqlite.

Quando considerar

  • consultas SQL sobre arquivos grandes
  • junções e agregações complexas
  • operação sem servidor
  • consultar Parquet em disco sem carregar tudo na memória, com SQL
  • consultar DataFrames do pandas ou Polars já em memória com SQL, sem cópia explícita
  • SQL com funções de janela para consultas analíticas sobre séries e resumos

Quando evitar

  • muitos processos escrevendo ao mesmo tempo
  • aplicações transacionais de alta frequência de escrita
  • cálculo numérico de engenharia, que deve ficar em NumPy; o DuckDB serve para consulta e agregação

Cuidados

  • um arquivo de banco aceita um processo escritor por vez
  • a versão 2.0 é recente; fixar a versão e conferir a compatibilidade do formato de arquivo de banco ao atualizar
  • somas de ponto flutuante em paralelo podem variar na última casa; ordenar e usar DECIMAL ou arredondamento declarado quando o resultado precisar ser reprodutível
  • o limite de memória e o diretório temporário para derramamento em disco são configuráveis; declarar ambos em consultas grandes

pandas

Biblioteca de DataFrames para filtrar, juntar e agrupar dados tabulares em Python.

Compete com polars, duckdb; coopera com numpy, parquet, plotly, pandera, xarray, scipy.

Quando considerar

  • dados tabulares com junções e agrupamentos
  • ecossistema maduro e amplamente documentado
  • integração direta com NumPy e Parquet
  • séries temporais com índice de datas e reamostragem (medições, vazões, precipitação)
  • bibliotecas de terceiros (Plotly, GeoPandas, pandera) que aceitam DataFrame do pandas

Quando evitar

  • volumes que não cabem com folga na memória
  • pipelines que se beneficiam de execução preguiçosa otimizada
  • junções e agregações muito grandes, em que Polars ou DuckDB tendem a usar melhor a memória (medir antes)

Cuidados

  • o comportamento de valores ausentes e os tipos dependem do dtype; definir dtype explícito
  • algumas operações copiam os dados
  • o pandas 3 adotou copy-on-write e removeu a atribuição encadeada; usar df.loc[mascara, coluna] = valor
  • o pandas 3 infere colunas de texto como dtype str (antes object) e a resolução de datas passou a ser inferida (microssegundos para texto); converter data para inteiro sem fixar a unidade (as_unit) dá valores diferentes
  • arredondamento e somas em ponto flutuante dependem da ordem das linhas; ordenar de forma explícita antes de agregar quando o resultado precisar ser reprodutível

Repositório: https://github.com/pandas-dev/pandas

Polars

Biblioteca de DataFrames com motor escrito em Rust, baseada em Apache Arrow e com API de expressões.

Compete com pandas, duckdb; coopera com numpy, parquet, plotly, duckdb, pandera.

Quando considerar

  • tabelas grandes
  • agregações e junções em paralelo
  • execução preguiçosa com otimização de consulta
  • expressões preguiçosas otimizam junções e filtros em tabelas grandes, lendo Parquet com seleção de colunas e filtro empurrados para a leitura
  • tipos estritos e valores nulos explícitos, sem conversões silenciosas de inteiro para float

Quando evitar

  • código existente que depende fortemente da API do pandas
  • bibliotecas que aceitam apenas pandas
  • código que depende do índice de linha do pandas (alinhamento por índice, reindex)

Cuidados

  • a API difere do pandas, pois não há índice de linha
  • na execução preguiçosa, o resultado só existe após collect()
  • o paralelismo pode alterar a ordem das linhas em agregações e junções; ordenar explicitamente (ou usar maintain_order) quando a ordem importar
  • a API ainda evolui entre versões; fixar a versão no projeto
  • a conversão para pandas ou NumPy (to_pandas, to_numpy) pode copiar dados e exige pyarrow ou numpy instalados

Repositório: https://github.com/pola-rs/polars

Formato de arquivo colunar, lido e escrito em Python pelo pacote pyarrow.

Compete com sqlite; coopera com pandas, polars, duckdb, geoparquet, pandera.

Quando considerar

  • leitura seletiva de colunas
  • compressão por coluna
  • trocar tabelas entre pandas, Polars e DuckDB preservando os tipos
  • guardar resultados de cálculo com esquema explícito (tipos, nulos) e metadados do arquivo

  • arquivos pequenos que são reescritos com muita frequência

  • os tipos são dinâmicos, não rígidos

pandera

Validação de DataFrames por esquemas declarados (tipos, faixas, nulos, unicidade e checagens estatísticas).

Compete com pydantic; coopera com pandas, polars, parquet.

Quando considerar

  • detectar na leitura um Parquet ou CSV com coluna faltando ou dtype trocado
  • coletar todas as falhas de uma tabela de uma vez com validate(lazy=True)
  • esquema único para pandas e Polars, quando os dois estiverem em uso

Quando evitar

  • validar um registro isolado ou um formulário (usar pydantic)
  • tabelas muito pequenas e estáveis, em que um assert simples basta

Cuidados

Pint

Biblioteca de grandezas físicas com unidades, que converte e recusa operações dimensionalmente inconsistentes.

Coopera com numpy, pandas, xarray, sympy, pydantic.

Quando considerar

  • fronteiras do sistema (entrada de usuário, planilhas, arquivos de terceiros) em que as unidades chegam misturadas e precisam virar SI
  • fórmulas de engenharia em que um erro de unidade (mm × m, L/s × m3/s) é um risco real
  • testes que conferem consistência dimensional da fórmula, não só o valor numérico
  • converter para SI na entrada e trabalhar com arrays NumPy puros no miolo do cálculo

Quando evitar

  • laços internos de cálculo pesado, em que o objeto com unidade atrapalha o desempenho e a vetorização
  • código que já segue a regra de unidade SI como sufixo do nome e não recebe dados em outras unidades
  • quando as unidades só precisam constar como metadado (atributos do xarray ou nome da coluna)

Cuidados

  • unidades com deslocamento (graus Celsius) têm regras próprias; somar duas temperaturas absolutas gera erro e diferenças usam delta_degC
  • usar um único registro de unidades (UnitRegistry) em todo o projeto; quantidades de registros diferentes não se misturam
  • o resultado de Quantity.magnitude é um número ou array NumPy sem unidade; converter para a unidade SI esperada antes de extraí-lo
  • nem toda função do NumPy e do pandas preserva as unidades; testar as operações usadas
  • a versão atual exige Python 3.12 ou mais recente

Repositório: https://github.com/hgrecco/pint

Pydantic

Compete com pandera; coopera com pint, sqlite, pandas.

Quando considerar

  • validar parâmetros de entrada de um cálculo (formulário web, JSON, YAML) antes de executá-lo
  • declarar faixas e restrições físicas dos campos (valor positivo, diâmetro mínimo) com mensagens de erro claras
  • gerar o JSON Schema do contrato de dados entre o cálculo em Python e a interface

  • cálculo numérico; o Pydantic valida estrutura e tipos, não faz a conta
  • quando uma dataclass simples e testes já bastam

Cuidados

  • o modo padrão é permissivo e converte tipos (a string "123" vira inteiro 123); usar strict=True quando uma conversão silenciosa for inaceitável

  • a versão 2 mudou a API em relação à 1 (validadores, model_validate, model_dump); código e tutoriais antigos podem não valer
  • o núcleo de validação é compilado (Rust), com wheels nativas por plataforma
  • a página da documentação oficial migrou de docs.pydantic.dev para pydantic.dev/docs

pyproj

Interface Python para a biblioteca PROJ, para transformar coordenadas entre sistemas de referência.

Coopera com shapely, geopandas, rasterio, numpy.

Quando considerar

  • converter SIRGAS 2000 geográfico (EPSG:4674) para UTM SIRGAS 2000 (zonas EPSG:31978 a 31985 no Brasil) e o inverso
  • converter coordenadas de EXIF de drone (WGS 84, EPSG:4326) para o UTM do projeto
  • declarar o sistema de coordenadas de cada camada (ortofoto, pranchas, rede) e transformar entre elas de forma explícita
  • cálculo geodésico (distância e azimute sobre o elipsoide) com a classe Geod

Quando evitar

  • quando o projeto é puramente local e todas as camadas já estão no mesmo CRS métrico
  • quando se quer manipular geometrias inteiras; combinar com shapely ou geopandas

Cuidados

  • usar Transformer.from_crs(origem, destino, always_xy=True); sem isso, a ordem dos eixos segue a definição da autoridade (latitude, longitude para EPSG:4326 e 4674) e o ponto sai invertido

  • a transformação depende da base de dados do PROJ (grades, datum shifts); registrar a versão do PROJ embutida na roda para reprodutibilidade
  • grades de datum opcionais podem não estar instaladas; conferir a operação escolhida (Transformer.description) e se a precisão é a esperada
  • a zona UTM deve ser escolhida pela longitude ou fixada no projeto; coordenadas fora da zona natural distorcem a escala
  • a PROJ vem embarcada nas rodas binárias; compilar do código-fonte exige PROJ instalada no sistema
  • fixar o EPSG como constante nomeada e usar sufixo de unidade nos nomes (leste_m, norte_m)

rasterio

Leitura e escrita de rasters georreferenciados (GeoTIFF e outros) sobre a GDAL, com arrays NumPy.

Coopera com numpy, pyproj, shapely, geopandas, xarray, pycolmap.

Quando considerar

  • ler ortofoto e MDS em GeoTIFF como arrays NumPy, com a transformação afim (pixel para UTM) e o CRS
  • amostrar o valor do MDS em pontos de uma rede ou de um perfil (sample)
  • recortar a ortofoto por polígono (mask) ou por janela, sem carregar o arquivo inteiro
  • reprojetar ou reamostrar um raster (warp)

Quando evitar

  • imagens sem georreferenciamento; PIL ou OpenCV bastam
  • rasters multidimensionais em NetCDF ou Zarr; considerar xarray
  • quando não se pode depender da GDAL (embarcada nas rodas binárias, mas pesada)

Cuidados

  • a transformação afim (transform) leva (coluna, linha) para (x, y); a linha cresce para o sul, então a altura do pixel costuma ser negativa
  • o valor nodata deve ser lido do arquivo e mascarado; tratá-lo como altitude real contamina volumes e perfis
  • ler em janelas (Window) para ortofotos grandes; ler tudo de uma vez pode estourar a RAM
  • o CRS do arquivo pode estar ausente ou errado; conferir contra o esperado (por exemplo UTM SIRGAS 2000) antes de usar
  • bandas uint8 (RGB) e float32 (MDS) têm tratamento diferente; não misturar na média
  • a reamostragem (nearest, bilinear, cubic) altera valores; escolher e registrar o método
  • a GDAL embarcada na roda pode diferir da do sistema; registrar a versão para reprodutibilidade

Shapely

Geometrias planas (pontos, linhas, polígonos) e operações geométricas, sobre a biblioteca GEOS.

Coopera com pyproj, geopandas, numpy, rasterio, ezdxf.

Quando considerar

  • área, comprimento, interseção, união, buffer e distância de polígonos e polilinhas em coordenadas métricas (UTM)
  • recortar trechos de rede (obra linear) por polígono de lote ou de pavimento
  • operações vetorizadas sobre arrays de geometrias (Shapely 2.x), em vez de laços Python
  • índice espacial (STRtree) para consultas de vizinhança entre muitas geometrias

Quando evitar

  • quando as coordenadas estão em graus (SIRGAS 2000 geográfico) e a medida deve ser em metros; projetar para UTM antes
  • quando é preciso 3D de verdade (volumes, interseção de sólidos); a biblioteca é essencialmente 2D
  • quando a tabela de atributos é o foco; usar geopandas, que embrulha o Shapely

Cuidados

  • a ordem das coordenadas é (x, y), isto é, (leste, norte) ou (longitude, latitude); misturar com (latitude, longitude) inverte o ponto
  • não conhece sistema de coordenadas; guardar o EPSG ao lado (geopandas ou pyproj) e nunca medir área ou comprimento em graus
  • a coordenada Z é carregada, mas as operações (área, distância, interseção) a ignoram
  • polígonos inválidos (autointerseção, anel aberto) dão resultado errado ou erro; checar is_valid e corrigir com make_valid
  • coordenadas UTM têm 6 a 7 dígitos; comparar com tolerância absoluta declarada, não com igualdade exata
  • set_precision altera a geometria; usar de forma explícita
  • {'determinismo': 'a mesma versão do GEOS dá o mesmo resultado; versões diferentes podem divergir em casos de borda'}

PyMuPDF

pytesseract

Interface Python para o motor de OCR Tesseract, que lê texto de imagens e devolve também posição e confiança por palavra.

Compete com paddleocr; coopera com pymupdf, pdfplumber, paddleocr, docling, numpy.

Quando considerar

  • prancha escaneada ou texto rasterizado sem camada de texto, depois de renderizar a página em imagem (por exemplo com pymupdf)
  • ler o carimbo e tabelas por região recortada, com image_to_data para obter caixa e confiança de cada palavra
  • texto em português, com os dados de idioma (traineddata "por") instalados
  • conferência cruzada de um valor lido do vetor contra o mesmo valor lido por OCR

Quando evitar

  • texto vetorial do CAD, que se extrai exato direto do PDF sem OCR
  • tabelas complexas ou texto girado sobre desenho denso, em que o Tesseract perde muito; avaliar paddleocr
  • cotas pequenas em desenho, sem pré-processamento

Cuidados

  • {'o pytesseract é apenas o invólucro': 'o programa Tesseract precisa estar instalado no sistema (apt, brew ou instalador no Windows) e o idioma português baixado em separado'}
  • licença Apache-2.0 do invólucro conforme o PyPI; a licença do Tesseract em si não foi verificada em 2026-11-02, conferir na distribuição usada
  • última versão publicada 0.3.13 em 2024-08, ritmo de manutenção baixo; acompanhar o repositório
  • o resultado depende da resolução, do contraste e do modo de segmentação (psm); fixar os parâmetros e a resolução de renderização no código
  • para o mesmo binário, a mesma imagem e os mesmos parâmetros espera-se a mesma saída; registrar a versão do Tesseract
  • confusões típicas entre 0/O, 1/l e vírgula/ponto em números exigem validação em Python (formato, faixa, soma)
  • cada chamada abre um subprocesso, o que pesa em muitas regiões pequenas

Skills

As ferramentas dizem com o que calcular; as skills dizem como o agente conduz uma tarefa: o passo a passo, quem executa e os cuidados. Cada skill aponta as ferramentas do repertório que usa. Página gerada a partir de repertorio/skills/ por vcm docs; edite os YAML.

Como as skills funcionam

Verificado em 2026-11-02 nas fontes citadas. O que não foi confirmado está marcado [não verificado].

O que é uma skill

  • Pasta com um SKILL.md: frontmatter YAML entre --- + instruções em markdown. Pode ter arquivos de apoio (reference.md, examples.md, scripts/). Fonte: https://code.claude.com/docs/en/skills (2026-11-02).
  • Frontmatter na plataforma: name (até 64 caracteres; só minúsculas, números e hífen; sem as palavras reservadas anthropic e claude) e description (não vazia, até 1.024 caracteres) são exigidos. Fonte: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview (2026-11-02).
  • No Claude Code todos os campos são opcionais (só description é recomendado); name padrão é o nome da pasta. Outros campos: when_to_use, disable-model-invocation, user-invocable, allowed-tools, context: fork, model, paths, license. Campos desconhecidos são ignorados sem erro. Fonte: code.claude.com/docs/en/skills (2026-11-02).
  • A descrição combinada (description + when_to_use) é truncada em 1.536 caracteres na listagem: colocar o caso de uso principal no começo. Fonte: idem.
  • Carregamento progressivo: nível 1, só nome e descrição (cerca de 100 tokens por skill) ficam sempre no contexto; nível 2, o corpo do SKILL.md entra quando a descrição casa com o pedido; nível 3, arquivos de apoio são lidos só se necessários e scripts rodam via bash, entrando no contexto apenas a saída. Fonte: platform.claude.com/.../agent-skills/overview (2026-11-02).
  • Depois de carregada, a skill permanece no contexto nos turnos seguintes; por isso, corpo curto (menos de 500 linhas). Também pode ser chamada direto com /nome-da-skill. Fonte: code.claude.com/docs/en/skills (2026-11-02).

Onde ficam (Claude Code)

  • Pessoal: ~/.claude/skills/<skill>/SKILL.md (todos os projetos da máquina).
  • Projeto: .claude/skills/<skill>/SKILL.md (versionado no repositório; vale para quem clonar).
  • Também: corporativa (managed settings), aninhada em subpastas, --add-dir e plugins (<plugin>/skills/..., invocada como /plugin:skill).
  • Precedência para o mesmo nome: corporativa > pessoal > projeto. Skill de plugin tem namespace e não colide. Skill do usuário substitui skill embutida de mesmo nome. Fonte: code.claude.com/docs/en/skills (2026-11-02).
  • Skills não sincronizam entre superfícies: claude.ai (zip em Configurações), API (/v1/skills) e Claude Code (sistema de arquivos) são separados. As skills prontas de documentos (pptx, xlsx, docx, pdf) não vêm no Claude Code. Fonte: platform.claude.com/.../agent-skills/overview (2026-11-02).
  • Sessões em nuvem não carregam plugins instalados na sua máquina nem os habilitados no .claude/settings.json. Fonte: https://code.claude.com/docs/en/discover-plugins (2026-11-02). Se skills de .claude/skills/ do repositório valem na nuvem: [não verificado].

Instalar skills de terceiros

  • Marketplace de plugins: /plugin marketplace add anthropics/skills, depois /plugin install document-skills@anthropic-agent-skills ou example-skills@anthropic-agent-skills. Fonte: https://github.com/anthropics/skills (2026-11-02).
  • Forma geral: /plugin install <plugin>@<marketplace>; no shell, claude plugin install ... (escopo user por padrão; --scope project para o repositório). Fonte: code.claude.com/docs/en/discover-plugins (2026-11-02).
  • Cópia de pasta: colocar a pasta da skill em ~/.claude/skills/ ou .claude/skills/. Fonte: code.claude.com/docs/en/skills (2026-11-02).
  • Seção específica sobre instalar skills soltas na página de skills: [não verificado] (os últimos ~18 mil caracteres da página não foram lidos).

Segurança

  • Oficial: usar skills só de fontes confiáveis (criadas por você ou da Anthropic); uma skill maliciosa pode mandar o Claude chamar ferramentas ou rodar código fora do propósito declarado, com risco de vazamento de dados. Auditar todos os arquivos (SKILL.md, scripts, recursos), procurar chamadas de rede inesperadas; tratar como instalar software. Fonte: platform.claude.com/.../agent-skills/overview (2026-11-02).
  • allowed-tools pode pré-aprovar ferramentas e a confiança do workspace não barra isso: revisar o campo em skills versionadas antes de rodar. !`comando` no corpo executa shell antes de o Claude ver o texto; disableSkillShellExecution desliga. Fonte: code.claude.com/docs/en/skills (2026-11-02).
  • Regra do projeto: ler SKILL.md e scripts/ antes de instalar qualquer skill de terceiros.

Boas práticas oficiais de escrita

Fonte: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices (2026-11-02).

  • Descrição em terceira pessoa, dizendo o que faz e quando usar, com termos-chave; evitar "ajuda com documentos".
  • Ser conciso: só o que o Claude ainda não sabe; dar um padrão-padrão em vez de lista de opções.
  • Graus de liberdade: instruções livres para tarefas flexíveis; script exato e sem parâmetros para operações frágeis.
  • Preferir scripts prontos para o que é repetível (mais confiáveis, economizam tokens); deixar claro se é para executar ou só ler; tratar erros no script.
  • Divulgação progressiva: arquivos de apoio a um nível de profundidade do SKILL.md; índice em arquivos com mais de 100 linhas; caminhos com barra normal.
  • Fluxos com checklist e laço validar-corrigir; plano intermediário validado por script em operações em lote.
  • Criar avaliações antes (mínimo de três cenários), comparar com e sem a skill e testar com Haiku, Sonnet e Opus.
  • Listar dependências; na API não há rede nem instalação de pacotes, no claude.ai depende da configuração, no Claude Code há rede total.

Lições da Fase 1 (registradas pelo próprio método)

  • O balanço pegou um problema real. O primeiro cartão (18b6b59 → 8fe6d37) propôs REVERTER por um alerta de segurança novo (B314, leitura de XML sem defusedxml). O alerta foi corrigido, não silenciado, e a troca (+1 dependência) aparece no cartão seguinte.
  • "Enxuto" precisa de contexto. Numa iteração que adiciona funcionalidade, SLOC e dependências sobem por definição. Sem normalização, a regra sempre pede decisão humana. Isso virou item do plano.
  • Determinismo depende de threads. Produto matricial e solve do NumPy mudam de hash entre 1 thread e 4 threads, e são estáveis com o número de threads fixo. Isso foi registrado no repertório do NumPy, e a métrica separada virou item do plano.
  • O gerente também erra. Um commit do Opus entrou com teste falhando, porque o código de saída do pytest foi mascarado num pipeline de shell. O balanço seguinte propôs REVERTER e o erro foi corrigido no commit seguinte. Regra: set -o pipefail em todo pipeline de verificação.
  • Agentes em paralelo duplicam utilidades. O executor da T005 não via o vcm.formatacao, criado ao mesmo tempo pelo gerente, e escreveu o seu próprio. O gerente unificou na integração. A especificação deve listar os módulos compartilhados em construção.
  • Interfaces entre executores paralelos divergem em semântica, não em assinatura. O executor da configuração tratou limites como sobreposição; o do semáforo, como lista completa. Com limites: {} o semáforo ficou todo cinza. Os testes de cada um passavam, e só o teste ponta a ponta revelou o problema. Regra: a especificação deve dizer o significado de cada campo compartilhado, e toda integração termina com um teste ponta a ponta.
  • O executor também corrige o gerente. A especificação do radar tinha um erro de sinal no expoente. O executor detectou, explicou e implementou o sinal correto.
  • Eficiência só se compara com o mesmo trabalho. Ao acrescentar um cálculo ao conjunto de referência, o tempo sobe por mais trabalho, não por código pior. Agora o hash da referência identifica o trabalho; se ele muda, tempo e memória viram informativos.
  • Ruído medido neste repositório (3 repetições): tempo de referência ±6% (faixa aceita 12%), pico de memória ±0,1%, tempo da suíte ±1,3%.
  • Tempo curto exige tolerância absoluta. No teste da main recém-publicada, uma iteração que só acrescentou um comentário deu DECISAO_HUMANA: o cálculo de referência de ~10 ms oscilou +23%. Correção com lógica de engenharia: piso absoluto de ruído (5 ms; 2 MB) e ruído automático = 2 × oscilação observada nas repetições do próprio snapshot. A mesma mudança agora dá SEM_GANHO, e a iteração sem semente continua REVERTER.
  • Portabilidade revisada antes da operação. O referencia.py gerado usava o módulo resource, que não existe no Windows, e no macOS a unidade de memória é outra. Agora a medição é portável (vcm.medicao), e a memória fica "sem medição" quando não há como medir, sem quebrar.
  • Projeto real ≠ projeto de exemplo. O primeiro projeto real não tinha pyproject.toml, tinha o pacote na raiz, dependências opcionais usadas pelos testes e um PDCA próprio com outra definição de "determinismo". Nenhum desses casos aparecia nos testes ponta a ponta com projetos criados do zero. Regra: diagnóstico só leitura antes de toda adoção.
  • Executores em paralelo precisam de cópias isoladas também no projeto de destino. Dois executores na mesma pasta do projetos_em_camadas compartilharam o ambiente uv: um rodava uv sync enquanto o outro rodava testes, e apareceram falhas fantasmas. Sozinho, o resultado foi estável. Regra: paralelo só com worktree; na mesma pasta, em sequência.
  • A régua do projeto de destino também pega o gerente. O determinismo.py do projeto em camadas reprovou uma lição registrada pelo Opus com formato errado. Respeitar e rodar as réguas existentes é parte da adoção.
  • Os logs de sessão mentem duas vezes se não forem lidos com cuidado. A mesma resposta aparece em várias linhas (até 7×), e a retomada da sessão noutro diretório copia o histórico para outra pasta de projeto. Somando tudo, o custo saiu US$ 64,55; filtrando por pasta, US$ 29,87; deduplicando globalmente pelo message.id, US$ 43,01, contra US$ 42,39 da plataforma. Regra: conferir toda telemetria contra uma fonte independente antes de confiar nela.
  • O gerente é o maior custo. Na rodada da Fase 2, Opus US$ 5,01 × Sonnet US$ 0,33 × Haiku US$ 0,02. O contexto longo da sessão principal (leitura de cache) domina. Isso é dado para a T003.

Estilo de código do repertório

Regras do mantenedor. Valem para humanos e para todos os agentes. Não são negociáveis: uma alteração que as viola é revertida, mesmo que melhore as métricas.

1. As quatro regras

# Regra Na prática
1 Python em português Nomes de variáveis, funções, classes, módulos, docstrings, comentários e mensagens em português. Palavras-chave da linguagem e APIs de bibliotecas ficam como são.
2 Python calcula Todo cálculo, agregação, estatística, conversão de unidade e decisão acontece em Python. Nenhum cálculo vai para outra linguagem.
3 HTML/JS apresentam HTML, CSS e JavaScript só exibem o que o Python já calculou: tabelas, gráficos, navegação e filtros visuais. JS não soma, não converte, não decide.
4 Sistema métrico (SI) Unidades do Sistema Internacional e as usuais no Brasil (m, mm, m³/s, L/s, kPa, m.c.a., kN, MPa, °C). Nada de pés, polegadas, psi ou galões, nem na entrada nem na saída.

2. Python em português

import numpy as np


def perda_de_carga_hazen_williams(
    vazao_m3s: np.ndarray,
    diametro_m: np.ndarray,
    comprimento_m: np.ndarray,
    coef_c: np.ndarray,
) -> np.ndarray:
    """Perda de carga distribuída por trecho (m), fórmula de Hazen-Williams (SI)."""
    return 10.67 * comprimento_m * vazao_m3s**1.852 / (coef_c**1.852 * diametro_m**4.87)
  • Nomes descritivos e sem abreviação obscura: vazao_m3s, não q; perda_total_m, não hf_t.
  • Acentos ficam fora dos identificadores (vazao, pressao, funcao) e dentro das docstrings e mensagens.
  • Mensagens de erro e de log também em português: raise ValueError("diâmetro deve ser positivo").
  • Termos técnicos sem tradução consagrada podem ficar como estão (hash, commit, parquet, worktree).

3. Unidade no nome

Toda grandeza física leva a unidade como sufixo do nome. Isso evita a classe de erro mais cara da engenharia, que é a de unidade.

Grandeza Sufixo Exemplo
comprimento, cota, diâmetro _m, _mm cota_terreno_m, diametro_mm
área _m2 area_secao_m2
vazão _m3s, _ls vazao_m3s
velocidade _ms velocidade_ms
pressão _kpa, _mca pressao_mca
força, tensão _kn, _mpa carga_kn, tensao_mpa
tempo _s, _ms, _min tempo_execucao_ms
memória _mb pico_ram_mb
adimensional sem sufixo, nome explícito fator_atrito, coef_c

A conversão de unidade é feita uma vez, na entrada, por função explícita (mm_para_m). O núcleo de cálculo trabalha só em SI.

4. Python calcula de forma vetorizada e determinística

  • NumPy primeiro para cálculo numérico: operações vetorizadas e matriciais, sem laço Python sobre elementos.
  • pandas ou Polars para dados tabulares: filtrar, juntar, agrupar. A escolha entre eles é tese, não gosto (ver T005).
  • Parquet para persistir tabelas; YAML para configuração; JSON Lines para logs brutos.
  • dtype explícito (float64 para engenharia) e np.random.default_rng(semente) sempre com semente.
  • Comparações numéricas com tolerância declarada (np.testing.assert_allclose), nunca == em float.
  • Cota, coordenada e nível usam tolerância absoluta (m), não relativa.
  • Funções puras no núcleo de cálculo: mesma entrada, mesma saída; nada de ler relógio, rede ou estado global.

5. HTML e JavaScript só apresentam

Python (numpy/pandas) --calcula--> tabela/figura pronta --serializa--> HTML (+ Plotly JS)
  • O Python gera o HTML, com Jinja2 para o texto e Plotly para gráficos, já com os valores finais.
  • O JavaScript se limita a renderizar gráficos, alternar abas, ordenar e filtrar tabelas. Valores exibidos vêm prontos e formatados.
  • Formatação brasileira na apresentação: vírgula decimal e ponto de milhar (1.234,56), datas dd/mm/aaaa. A formatação também é feita em Python (vcm.formatacao).
